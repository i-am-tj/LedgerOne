# ADR-008 — Typed local account operations and opening audit

Status: owner approved opening-audit direction and mandatory UI scope for isolated local development. Reconciliation is explicitly approved as audited comparison only. Implementation remains subject to source review and reviewed merge.

The first account flow creates the account and optional opening in one transaction. Zero opening creates no journal or OPENING receipt. A signed amount is interpreted in the physical account's normal sign convention. Nonzero openings use exactly two equal absolute INR quantities, one physical account and one OPENING_EQUITY counterpart. The original marker remains unique.

Migration008 explicitly maps ledger.opened to OPENING in the existing financial audit validator. New OPENING receipts require exactly one scoped immutable audit identifying the posted opening journal and marker. The INSERT-only deferred check leaves existing receipts unchanged. Existing POST/REVERSE/CORRECT receipt-audit SQL tightening stays excluded.

Migration009 supplies immutable typed account receipts/events for account creation, rename, archive, restore and reconciliation. Every receipt requires one scoped event with matching action and result snapshot. Creation and opening use the existing shared executor, SERIALIZABLE isolation, three attempts, one ten-second deadline, authentication, attestation, account locks and uncertain-COMMIT/ROLLBACK handling. No independent executor or nested transaction is introduced. Account commands use an exclusive owned-workspace lock before sorted account locks; existing journal commands retain their workspace key-share followed by sorted account locks. This prevents concurrent first-use system-equity creation and maintains workspace-before-account ordering. Replay precedes mutable archive checks and validates its immutable receipt/event and opening evidence. Account keys are owner/workspace-scoped in account_command; the linked financial opening uses a server-generated receipt key.

Opening journal descriptions capture the initial account name. Immutable account events retain lifecycle snapshots. UI headings use current names while opening activity retains its original description. Reconciliation stores the exact normal-sign ledger balance, statement balance and ledger-minus-statement discrepancy at the chosen instant. It does not post an adjustment or overwrite a balance. Future discrepancy adjustment needs a separate reviewed accounting contract.

Only the typed account handler can receive the explicitly provisioned local writer. The test server wrapper validates loopback test configuration and a generated disposable database name, provisions a restricted role and captures its live invariant manifest. Its private capability file uses mode0600 and is removed on shutdown. Ordinary development/production profiles cannot activate that capability. The native generic financial route retains null capability even during the browser demonstration. Published production grants and migrations001–007 are unchanged.

The required real desktop/mobile browser scenario creates SBI Savings with ₹50,000, refreshes, reads opening history, renames while preserving the initial description, records a ₹49,500 statement and ₹500 discrepancy, archives/restores and verifies a second user's denial. UI01–UI04 and this browser gate are required before S07/P1-E3 closure.

As-of read boundaries send explicit ISO timestamptz parameters. The Prisma runtime connection uses UTC so returned timestamps retain the original instant on non-UTC servers. Quantities use SQL numeric text/BigInt and currency-specific scales. Overview INR totals exclude foreign-currency accounts. Activity/event panels currently show up to100 recent entries; complete pagination remains a disclosed UI limitation.
