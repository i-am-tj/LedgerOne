# ADR-006 — Authenticated POST, immutable replay and closed production exposure

> Current status (2026-11-12): S06B completed/reviewed merge `5af4c19`; S06C predecessor satisfied, planning acceptance pending. Full S06 gate closed, Phase 1 incomplete, normal-runtime financial writes disabled. [Verified closure](../reports/S06B_CLOSURE.md).

Date: 2026-11-11. Story P1-S06B / PR #21. Status: implemented/tested locally; final-head accounting/security review and reviewed merge pending. Planning PR #20 was reviewed/merged before implementation; that approval is not implementation acceptance.

The only HTTP command is strict raw INR POST. The shared server-only handler derives identity from the real verified, unexpired, currently allowlisted database session. Client owner/actor/draft/revision/hash/FX fields are rejected. Each attempt revalidates the session and owned workspace. No new sign-in provider, consumer template or UI is added.

The validator produces frozen exact quantities and a versioned canonical tuple. Receipt uniqueness is scoped to owner/workspace/key. After authentication/workspace authorization, replay selects the durable journal/postings/audit before checking new-post account eligibility. Historical DTOs contain no account names/archive flags; archived or renamed accounts cannot invalidate an authorized same-key replay. Changed semantics conflict. Duplicate legs remain distinct. Future hash protocol changes need explicit durable receipt compatibility; v1 cannot be silently replaced.

New commands lock accounts in deterministic UUID order, then create receipt/private draft/postings/finalization/mandatory financial audit in one SERIALIZABLE transaction. Raw commands require a bounded reason included in hash/audit; future consumer templates may supply a controlled default without ordinary users typing one. Saved editable drafts and their incomplete S05 revision protection remain excluded. Nothing exposes uncommitted drafts or a confirmation token.

The financial executor uses the existing `pg` dependency for explicit isolation, row locks, commit-boundary handling and unwrapped PostgreSQL SQLSTATEs. Prisma remains the schema/migration and auth adapter layer; no new dependency or alternative database is introduced. Only known full-transaction aborts 40001/40P01 and the named receipt-key contention are retried within three attempts/10 seconds with bounded jitter and fresh snapshots/authorization. Transaction-local PostgreSQL 17 timeouts bound in-transaction work; pooled settings reset. An uncertain COMMIT destroys the connection and requires same-key recovery rather than an invented rollback, automatic new key or partial retry.

There is deliberately no production enable switch. The actual Next adapter supplies null capability. Positive execution construction is restricted to generated disposable loopback test databases, non-owner roles and trusted invariant manifests, with attestation before attempts. Fault barriers are trusted test-code callbacks, not public routes/headers. Real HTTP integration uses the same handler; browser regressions prove the actual Next route stays disabled. This does not prove a hosted/private production command profile. A reviewed S06D exposure/attestation/grant mechanism is required before any production write; published financial grants stay SELECT-only.

No migration or S05/S06A invariant changes. Recovery is preserve immutable outcomes and disable exposure, never rewrite applied SQL/receipts/audit. S06C corrections, S07 OPENING audit/account lifecycle and the complete S06 write gate remain separate reviewed work. Evidence and limits: [P1-S06B report](../reports/P1-S06B.md).

Adversarial review correction (2026-11-12): total body ingestion is capped at five seconds/128 KiB and observes cancellation without awaiting untrusted stream cleanup. Closed capability rejects before body consumption. An abort observed before sending COMMIT rolls the private command back; once COMMIT may have been sent, the outcome is resolved only through its acknowledgement or a fresh same-key lookup. Inspector snapshots have actual database statement/transaction limits and unusable own connections are destroyed; promise deadlines alone are insufficient. Request and execution budgets are separate. No production exposure or business template is added; future consumer business APIs must not offer generic raw posting as a bypass around their typed accounting rules. See S06B_ADVERSARIAL_REVIEW for exact findings and regressions.
