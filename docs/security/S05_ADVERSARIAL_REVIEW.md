## Findings

### A05-01 — Medium — Draft revision does not version header financial meaning

**Classification:** confirmed version-coverage gap; not a demonstrated unbalanced commit or mutable posted journal. The revision is safe as a child-edit/MVCC mechanism, but is not a complete optimistic version of a draft.

**References:** `prisma/migrations/202611110004_ledger_schema/migration.sql:301` increments revision only for posting/marker writes; `prisma/migrations/202611110006_reversal_predecessor/migration.sql:10` guards draft identity but does not increment revision for `effectiveAt`, `description`, kind or reversal-target changes. `prisma/schema.prisma:239` and `:242` expose effective date and revision. Existing races at `tests/integration/ledger-schema.test.ts:631` and `:671` exercise child edits, not header-version checks.

**Reproduction:** create a balanced two-leg draft dated January 1; observe revision 2. In another committed transaction change `effectiveAt` to February 1 and description. Revision remains 2. Finalize using `WHERE id = :draft AND revision = 2`, a new POST receipt, and posted timestamp. Commit succeeds at February 1. Independent probe `stale_header_revision_compare` recorded `2 → 2`, accepted finalization and `2026-02-01T00:00:00.000Z`.

**Impact:** a future service using this revision as the version of the entire previewed transaction can accept a stale confirmation and book the transaction in a different reporting/budget period. The existing parent row writes still reject stale MVCC snapshots; this is a separate application-level optimistic concurrency issue. No current financial endpoint exposes it.

**Recommended correction:** before relying on revision CAS, make every meaningful draft header/child change participate in a server-owned monotonic version, or implement an explicit full-command version/hash protocol. Reject caller-controlled/reset versions. Define whether finalization compares the full draft or constructs an entirely private draft from one validated command. Do not describe the existing counter as a full draft version. Any DB correction must be a forward migration; do not edit 004–006.

**Regression required:** two clients read one version; one changes date/description/kind/target; the other's finalize/edit returns a conflict with no receipt, journal or audit side effects. Test both READ COMMITTED stale version CAS and actual REPEATABLE READ/SERIALIZABLE snapshots; preserve child-edit and successful fresh-version cases.

### A05-02 — Medium — CORRECT receipt can reverse its own replacement

**Classification:** confirmed operation-semantic permissiveness. This does not bypass exact multiset reversal, duplicate-reversal prevention or cycle prevention. Command-target validation is planned S06 work, so this is not a current public API exploit.

**References:** `prisma/migrations/202611110004_ledger_schema/migration.sql:325` checks only one GENERAL plus one REVERSAL for CORRECT; `prisma/migrations/202611110006_reversal_predecessor/migration.sql:18` requires POSTED at link time, including a journal posted earlier in the same transaction. The valid correction test at `tests/integration/ledger-schema.test.ts:811` does not cover this case. `docs/ACCOUNTING.md:45` describes a correction of an original plus an optional replacement.

**Reproduction:** in one transaction insert a CORRECT receipt C; create/post GENERAL replacement G under C; create R with `reversesJournalId = G`, exactly negate G and post R under C; commit. Both counts and predecessor checks pass. Probe `correction_targets_own_replacement` accepted both journals. No existing transaction was corrected; the pair nets to zero.

**Impact:** a receipt can be structurally successful while having no intended correction target. A buggy S06 orchestrator could report success without correcting the requested purchase. Immutable history, individual journal balance and an acyclic reversal graph remain intact.

**Recommended correction:** S06 must require an explicit authorized original target and verify that the reversal points to that target, not the current operation's replacement. Add defense in depth rejecting a CORRECT reversal whose predecessor belongs to the same operation. The receipt counts alone must not be presented as proof of correction intent.

**Regression required:** reject same-operation predecessor/replacement confusion atomically, preserving the original transaction and leaving no receipt/audit. Positive correction must reverse the requested original, keep its original history and commit exactly one replacement. Include concurrent correction of the same original and the supported reversal-of-reversal chain.

### A05-03 — Medium — Checksums and Prisma diff do not detect invariant catalog drift

**Classification:** confirmed verification gap, not observed drift or an unprivileged escalation. The old review already notes Prisma's limitation; the negative experiment now demonstrates its consequence.

**References:** `scripts/rehearse-production-schema.ts:72` diffs only Prisma-supported schema objects; `tests/integration/ledger-schema.test.ts:793` compares applied-file checksums, not live trigger/function/CHECK definitions. `docs/PROGRESS.md:322` and `:335` must be read within those limits.

**Reproduction:** on a newly migrated scratch DB obtain Prisma diff exit 0; as its owner drop `posting_fx_not_enabled`, `journal_balanced_at_commit` and `posting_balanced_at_commit`. Repeat `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`: still 0. All six file hashes still match `_prisma_migrations`. A freshly created schema rehearsal in a separate database cannot attest that another already-running database retains those objects. This is consistent with [Prisma’s documented diff feature coverage](https://docs.prisma.io/docs/cli/migrate/diff); the removal experiment above is local evidence for this exact version.

**Impact:** accidental privileged DDL/removal of accounting protections can escape these particular checks. Existing behavioral tests cover important rejection cases but are not an exhaustive deployed-catalog attestation. A malicious migration administrator remains trusted regardless of checksums.

**Recommended correction:** add a reviewed invariant catalog manifest/comparison to a fresh migration replay, covering CHECK definitions/validation, trigger definitions/enabled state, function bodies/search paths/security attributes and grants/ownership. Run behavioral negatives under the actual writer role. Fail the deployment/write-enablement gate on unexpected differences; never repair history by rewriting applied migration files.

**Regression required:** separately remove a CHECK, disable a trigger and alter a helper body in disposable DBs; the invariant-drift check must fail even while Prisma diff and applied-file checksums pass. Include extra/missing/unfinished migrations and changed applied-file hashes.

**Current evidence:** independently compared 89 constraint, non-internal trigger and function definitions from a fresh six-migration public-schema replay with both existing local test and development catalogs: zero differences. This sample comparison does not include all ACL/ownership/index/type drift. All six existing test DB migration names and file checksums match. Private-schema provisioning/grants were separately rehearsed. No hosted catalog was inspected.

### A05-04 — Low — Historical display names need an explicit S07 history policy

**Classification:** confirmed mutable metadata, documented by design; forward reporting/audit risk rather than a current accounting classification or report defect.

**References:** `prisma/migrations/202611110004_ledger_schema/migration.sql:270` omits name/archive/update metadata from immutable identity; `prisma/schema.prisma:196` stores only the current account name; `src/lib/ledger/queries.ts:16` returns that name. `docs/ACCOUNTING.md:41` calls for historical names/context or revisions, while `:62` permits future account renames.

**Reproduction:** post against an EXPENSE account named Groceries; rename it Rent. A historical posting joined to that account now displays Rent. The independent SQL probe also confirmed no automatic audit event. The account ID/class/kind/currency and posted amounts did not change. No current financial reporting UI performs this join, and production financial UPDATE grants are absent.

**Impact:** a future historical report can imply a changed purchase purpose if current labels are mistaken for original context. Account names are not yet category records; this is not evidence that stored category allocations changed.

**Recommended correction:** S07 must distinguish current account labels from original transaction/classification context, preserve snapshots or auditable name revisions where original labels are promised, and audit renames/archive/restore. S06 must not infer immutable transaction purpose solely from a mutable account name.

**Regression required:** rename/archive an account after posting; historical quantities/classifications and original-context display remain accurate; current-name display is explicit; audit records the authorized change and old/new context. Unauthorized metadata changes produce no effects.

### A05-05 — Medium — Financial HTTP authorization remains unproved until S06/S07

**Classification:** planned feature/test boundary, not a discovered IDOR. No financial HTTP endpoint exists in this revision. Severity describes the consequence of treating helper tests as endpoint authorization proof.

**References:** `src/lib/ledger/queries.ts:5` trusts a supplied nonblank Actor; `src/lib/ownership/service.ts:4` defines an internal structural Actor. `tests/integration/ledger-schema.test.ts:267` supplies actors directly. The real existing workspace boundary derives identity from a verified session at `src/lib/ownership/http.ts:68` and enforces mutation origin at `:77`. `docs/setup/supabase-runtime-grants.sql:10` keeps financial tables SELECT-only. Those shared SQL credentials do not implement per-user RLS.

**Failure scenario:** a future handler constructs Actor from a body/query/header owner rather than `getOwnerSession`; supplying another allowed user's ID then makes the otherwise correctly scoped helper read that user's data. A two-owner FK test cannot detect this wiring error. Current ledger helpers have no production route callers, so this scenario is not presently reachable.

**Impact:** future cross-user disclosure/financial writes if the service boundary is miswired. `server-only` prevents client bundling; it is not authentication.

**Recommended correction:** derive actor only from a currently verified, unexpired, allowlisted session; reject supplied ownership fields; authorize every referenced entity inside the transaction; preserve uniform foreign/missing 404 behavior, strict CSRF-aware origins and bounded validated inputs. Keep financial write grants disabled until actual handlers and tests exist.

**Regression required:** real handlers with two authenticated owners, anonymous/expired/revoked/removed-allowlist sessions, guessed IDs, injected owner/workspace/account IDs and cross-origin requests. Assert status plus unchanged financial rows, operation receipts and audit on every denial. Workspace-only tests do not satisfy this requirement.

## Precise handoff conditions

Before starting S06 implementation:

1. Record this decision and include it in S05 review; complete the required reviewed S05 merge. This agent verification does not fabricate external peer review or merge evidence.
2. Make A05-01/A05-02 explicit S06 acceptance requirements. Choose and document either complete draft versioning or private atomic command drafts; require correction-target identity outside the current operation's replacement. A revision-only full-draft contract is not approved in its present form.
3. Retain published financial SELECT-only grants and the INR FX gate. S06 planning/implementation is not permission to enable runtime writes, migrate hosted Supabase or deploy.

Before S06 financial writers are enabled or S06 is accepted:

1. Resolve/test A05-01 and A05-02 for the chosen command contract; use additive migrations for any SQL changes. Add an invariant-drift check or explicit equivalent attestation for A05-03 to the write-enablement gate.
2. Implement and test the actual authenticated financial handlers (A05-05), including ownership of target originals, workspaces, accounts and idempotency namespace. No caller-owned Actor or loose payload passthrough.
3. Define canonical command hashing, same-key/same-payload replay of the same outcome and same-key/different-payload conflict. Handle racing requests, commit-time failures, dropped responses and bounded full-transaction retries on 40001/40P01. A receipt must not survive any failed command; duplicate-key failure alone is not successful idempotent replay. Whole-transaction retry follows the [PostgreSQL isolation rules](https://www.postgresql.org/docs/17/transaction-iso.html).
4. Add financial audit schema support in a forward migration. Currently `audit_event_action` in `prisma/migrations/202611110003_ownership_audit/migration.sql:17` permits only `workspace.created` and `workspace.renamed`. S06 must link financial target/operation and actor/request/reason sufficiently to reconstruct the event and insert it in the same transaction; new financial action names currently fail the CHECK. Do not drop audit immutability or claim existing fixture receipts are audited commands.
5. Validate canonical monetary strings before SQL binding, nonempty/bounded inputs, finite dates, allowed effective-date/backdating behavior and server-generated posting timestamps. Define deterministic account/journal lock order, conflict/error mapping and transaction/lock timeouts. Include serialization/deadlock/reversal races and success after retry, not only database rejection.
6. Keep unsupported FX/refunds/reconciled-period changes and business-template claims out of the exposed contract. S08, not S05 fixtures, implements card settlements/FD/loan/principal/income classification. Phase 1 cannot pass before those canonical scenarios are implemented and tested.

For S07 compatibility, before account mutation/opening/reconciliation acceptance:

- Define authorized audited archive/restore behavior; either reject archived corrections atomically with a useful recoverable error or provide a reviewed controlled workflow. Do not temporarily unarchive silently in a public command.
- Treat the opening marker as original provenance. Derive a corrected opening through its linked reversal/GENERAL replacement operations; do not insert a second marker or count only `kind=OPENING`. Preserve replacement provenance and test repeated correction/undo. A zero opening can be represented by no opening entry; do not invent zero-value postings.
- Use all relevant posted legs, including opening/reversal/replacement chains, for balance-as-of and native statement reconciliation. Archived accounts still retain their balances/history. Define reconciled-period adjustments and classify explicit differences; never overwrite a stored balance.
- Resolve historical name/context display and audit policy (A05-04). Add the needed audit actions, reconciliation markers and tests by forward migration; these S07 models/workflows do not exist yet.
