## Delivered behavior

The existing `/transactions` page combines expense, card purchase, income, transfer, card settlement, FD funding, FD principal return and loan repayment. One row represents one original business operation, not its posting legs. Original immutable account/category names, description, effective date, recording time and loan components remain visible. Recording time is the immutable business-context creation time, not a claim about COMMIT acknowledgement time. Card purchases and settlements have separate labels; movements explicitly have no consumption/income effect.

A single read-only REPEATABLE READ snapshot supplies history, full posted-ledger income/consumption, account balances and INR assets/liabilities/net worth. Amounts use SQL numeric sums and BigInt/string conversion, including totals above both JavaScript safe integers and the per-posting maximum. Drafts never count. Inclusive effective-time cutoffs apply to all totals/balances. Explicit UTC serialization avoids raw-adapter timezone reinterpretation; UI dates identify India time. Future-effective originals stay visible but do not inflate current totals.

History is the latest100 original business operations, ordered by immutable recording time descending and operation ID descending. Each family contributes at most101 SQL candidates; only101 are globally selected to identify whether more exist. Summaries cover the complete posted ledger independently of this cap. No pagination or unbounded full-history retrieval is claimed. GET supports an optional owned workspace and strict timestamp `asOf`; default scope is all owned workspaces/current time. Foreign workspace404, malformed/unknown/duplicate filters400.

Reversed originals remain visible with linked journal/operation/effective dates. CORRECT includes replacement-journal context without fabricating an extra original purchase. One immediate follow-up reversal link prevents claiming a reversed contribution stays zero when its reversal is reversed. Deeper chains are not recursively expanded; complete ledger totals still include every posted entry. No correction UI or new consumer mutation is introduced. Repeated GETs are read-only, including through an actual SELECT-only reader.
