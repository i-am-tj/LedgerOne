# P1-S05 — Chart of accounts and financial schema

**ID:** P1-S05 | **Title:** Chart of accounts and financial schema | **Epic:** P1-E3 | **Priority:** P0 | **Dependencies:** S04/S04A implemented; published CI green; user explicitly authorized S05. Core INR/sign/reversal rules and staged FX support approved. Independent review/merge is not assumed.

**User story:** As an allowed owner, I want exact, owned ledger records whose accounting invariants survive direct SQL and concurrent writes.

**Inputs (data/API/preconditions):** Owned workspace; fixed account kind/class/currency; canonical decimal-string amounts parsed to bigint minor units; draft journal with positive debit/credit legs; server operation key/hash; opening provenance; immutable manual FX quotes. Functional INR. Reference scales: INR/USD/EUR/GBP 2, JPY 0, KWD 3. User approved foreign accounts/rates with foreign posting disabled pending detailed FX review.

**Outputs (UI/API/schema/docs):** Account/Journal/Posting/OpeningBalance/Currency/FXRate/LedgerOperation schema; additive migrations/schema version 6; SQL ownership/kind/balance/lifecycle constraints; exact money/chart utilities; scoped financial reads; PostgreSQL adversarial tests; accounting ADR/recovery evidence. No S06 posting API or S07 account CRUD/reconciliation UI.

**Implementation tasks:**

- [x] Record accounting ADR and approved FX boundary.
- [x] Implement exact money parsing/formatting and chart sign conventions.
- [x] Add scoped schema, keys/indexes and immutable reference currencies.
- [x] Enforce commit-time balancing, posted immutability, opening/reversal structure and successful operation receipts.
- [x] Serialize draft edits/finalization and account archive races.
- [x] Test actual PostgreSQL constraints, scoped reads, no-side-effect negatives and private-schema portability.
- [x] Update docs/traceability and run required checks; prepare concrete accounting/security review evidence.
- [x] Record owner human accounting/security review and actual S05 merge before S06 (evidence below; no native self-approval fabricated).

**Acceptance criteria (Given/When/Then):** Given invalid/unbalanced/cross-owner/currency-incompatible legs, when a transaction commits as posted, then DB rejection rolls back the entire transaction. Given a valid INR journal, when posting atomically, then debits equal credits and history is immutable. Given concurrent draft edits/finalization/archive, when committing, then only valid serialized results survive. Given two owners, when IDs are guessed, then financial queries return no foreign records. Given foreign accounts/rates, when posting foreign quantities, then explicit staged FX policy rejects them. Given opening/reversal markers, when posted, then exact accounting structure is enforced.

**Unit tests:** Scale/sign/range beyond JS safe integers, canonical amount/rate syntax, formatting and chart mapping. No FX rounding implementation.

**Integration/E2E tests:** Real PostgreSQL deferred/direct-SQL negatives, two-user financial reads, operation uniqueness/immutability, opening/reversal structure and concurrent lifecycle races. Existing browser suite provides UI/auth regressions; no new financial UI is claimed. Fresh private-schema/restricted-role rehearsal.

**Failure/edge cases:** Empty/one-sided/zero/negative/overflow legs; currency/owner mismatch; unsupported FX; self/duplicate/inexact reversal; moving posting parents; deleting/truncating posted history; orphan operation/opening metadata; stale snapshots. SQL type coercion is not a public input contract; future commands must validate decimal strings before binding.

**Rollback/migration notes:** Reference currency rows are system metadata, not demo money. Preserve existing auth/workspaces. Transactional additive migration; deployed upgrades require a backup. On failure disable writes and forward-repair; never reset/drop posted history or edit applied SQL. Destructive recovery only on explicitly disposable DBs. No production migration/deployment.

**Definition of done:** Demonstrated owned/exact behavior, authorization, safe recovery, required checks/docs green, accounting/security review and reviewed merge. S06 orchestration/audit/retries and S07 account/opening/reconciliation workflows remain separate; phase gate stays blocked.
