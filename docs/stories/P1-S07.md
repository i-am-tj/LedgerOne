# P1-S07 — Account lifecycle, opening history and reconciliation

**ID:** P1-S07 | **Title:** Account lifecycle, opening history and reconciliation | **Epic:** [P1-E3](https://github.com/i-am-tj/LedgerOne/issues/2) | **Priority:** P0 | **Dependencies:** P1-S06 reviewed completion and passing write gate; finding A05-04; controlled archived-correction review

**User story:** As an allowed owner, I want to maintain accounts and reconcile posted balances without rewriting financial history.

**Inputs (data/API/preconditions):** Authorized account commands, explicit opening provenance/effective dates, statements, posted opening/reversal/replacement chains and approved metadata display policy.

**Outputs (UI/API/schema/docs):** Account UI/API, audited create/rename/archive/restore, chain-aware opening/balance-as-of queries, reconciliation markers/API by additive migration.

**Implementation tasks:**

- [ ] Implement account metadata history/audit with explicit current-name vs original-context presentation.
- [ ] Define reviewed archive/restore and controlled correction behavior; prohibit silent temporary unarchive.
- [ ] Post new openings atomically through validated authorized S06 primitives with OPENING receipt/marker, linked audit, idempotent replay and duplicate-opening concurrency tests.
- [ ] Add a reviewed additive migration for an explicit opening audit action (proposed `ledger.opened`): extend the action CHECK and deferred target validator to require OPENING operation + exact posted OPENING journal + scoped original opening marker. Migration 007 intentionally does not permit this action; never reuse `ledger.posted` or edit applied 007 to bypass it.
- [ ] Retain unique original opening marker; derive corrected openings from reversal/GENERAL replacement chains.
- [ ] Compute balance-as-of using all posted legs and native quantities, preserving archived balances.
- [ ] Add reconciliation markers and explicit adjustment/reason workflow; reject silent balance overwrites.
- [ ] Test two-user handlers, immutable context and account lifecycle/concurrency.

**Acceptance criteria (Given/When/Then):**

1. Given a posted transaction, when its account is renamed/archived, then historical quantities/classifications remain accurate and original-context policy is honored with an atomic audit.
2. Given a corrected opening, when querying opening or balance-as-of, then original marker plus linked corrections are interpreted once without a second opening marker.
3. Given archive/restore/correction/reconciliation races, when commands commit or fail, then reviewed permissions/period rules and atomic ledger/audit hold.
4. Given a new opening, when confirmed through the authorized handler, then one OPENING receipt, journal, original marker and matching immutable audit commit atomically; a wrong operation/target/owner/marker or failed audit rolls every new row back. Same-key replay creates nothing; concurrent duplicate openings leave one original marker. Until the additive audit contract is reviewed, the opening command remains unavailable.

**Unit tests:** Normal balances, effective-date selection, opening-chain derivation and metadata labels.

**Integration/E2E tests:** Actual account CRUD/archive/restore authorization, native statement/as-of reconciliation, repeated opening correction/undo and retained archived balances. Fresh/upgrade opening-audit migration; valid opening and wrong-kind/target/owner/marker rejection; injected audit failure rolls back receipt/journal/postings/marker/audit; replay and duplicate-opening contention; legacy and POST/REVERSE/CORRECT audit compatibility retained.

**Security and concurrency regression tests:** A05-04 historical metadata regression; wrong-owner updates, closed/reconciled-period adjustments, archive-vs-correct/rename races and audit rollback.

**Failure/edge cases:** Zero opening (no zero posting), immutable original marker, foreign accounts with posting disabled, duplicate opening, reconciliation discrepancy, backdating/reconciled history.

**Rollback/migration notes:** Additive audit/reconciliation schema; archive rather than delete referenced accounts. Use explicit forward journal adjustments and preserved original context; never overwrite balances.

**Definition of done:** Behavior demonstrated; strict validation and session-derived authorization; atomic ledger/receipt/audit rollback; additive/checksum-safe migrations with recovery; required formatting/lint/typecheck/unit/integration/build checks green; applicable browser/accessibility checks; accounting/security review at the final head; reviewed merge. Compilation, an agent review, or a tracking issue alone is not completion.
