## Migration and recovery

`202611110001_platform` creates only `app_metadata` and its schema marker. No user or financial data exists. Rehearse on a disposable database. Prefer an additive forward repair after any deployed migration; never edit applied SQL. Before a future release, back up data and retain an app/schema-compatible rollback artifact. For a disposable local-only database the recovery path is deleting and recreating its Compose volume, then `db:migrate`; this destroys its records and is never an approved production rollback. Removing this migration from a persistent deployment requires a reviewed forward migration, not a casual DROP.

Security: `.env` ignored with example exception, local-only bind defaults, no sensitive health output, no client DB import, no public deployment. Auth and tenant data are intentionally absent until P1-S03/P1-S04. Dependency advisories must be reviewed, not silently dismissed.

Definition of done: demonstrated acceptance, formatting/lint/typecheck/unit/integration/build green, no undocumented setup, no committed secrets, recovery notes and docs current, checks linked to a commit, review and merge recorded. Until then this story is not done.
