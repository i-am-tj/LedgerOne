# P1-S06B — Authenticated POST with canonical replay and atomic audit

**ID:** P1-S06B | **Title:** Authenticated POST with canonical replay and atomic audit | **Epic:** [P1-E3B](https://github.com/i-am-tj/LedgerOne/issues/4) | **Priority:** P0 | **Dependencies:** P1-S06A reviewed merge and required checks green; trusted session/ownership boundary

**User story:** As an allowed owner, I want to submit a validated journal once with a verifiable financial audit trail.

**Inputs (data/API/preconditions):** Server session; explicit owned workspace; strict POST discriminator; idempotency key; 2–500 bounded INR legs; finite offset-bearing effective timestamp; description/reason. Actor/request ID/postedAt generated by server.

**Outputs (UI/API/schema/docs):** Server-only posting service and actual POST handler under default-disabled financial write exposure; canonical hashing/replay; bounded whole-transaction retry; linked financial audit.

**Implementation tasks:**

- [x] Define bounded strict discriminated payload and body size; reject ownership/session/posting timestamps, draftId/revision and unknown fields.
- [x] Validate decimal strings with existing exact money parsers before SQL; enforce INR and leg limits.
- [x] Version canonical hashing over normalized semantic payload + trusted owner/workspace; preserve duplicate leg multiplicity; exclude generated IDs/request IDs and secrets.
- [x] Authorize workspace and every account in transaction; lock accounts in stable UUID order and recheck archive/type/currency.
- [x] Create private DRAFT, legs, receipt, finalization and linked audit in one DB transaction.
- [x] Implement same-key/same-hash immutable original outcome replay even after account archive/rename, same-key/different-hash conflict, race recovery and lost-response replay.
- [x] Implement bounded complete-transaction retries for 40001/40P01, lock/statement timeouts and sanitized stable errors.
- [x] Test real handler sessions and temporary writer role only on isolated DBs; keep production grant artifact read-only.

**Acceptance criteria (Given/When/Then):**

1. Given valid owned balanced POST, when called through the handler, then exactly one posted journal/receipt/linked audit commits and bigint quantities serialize as strings.
2. Given two concurrent requests with identical key/payload, when both finish, then both reference the same original committed outcome with exactly one operation/audit; replay also succeeds after archive/rename and recovery uses a fresh snapshot.
3. Given the same key with different semantic data, when retried, then return conflict without altering the first outcome.
4. Given foreign IDs, invalid/expired/revoked sessions, cross-origin mutation or malformed/oversized input, when invoked, then deny with no financial side effects.
5. Given stale persisted draft ID/revision fields, when submitted, then reject as outside the private-atomic-draft contract; never finalize a saved mutable draft.
6. Given serialization/deadlock abort or a failure at each mutation boundary/commit, when retried or exhausted, then no partial outcome survives; successful replay retains the original audit.

**Unit tests:** Canonical golden vectors, property order/normalization/duplicate multiplicity, exact amounts/finite dates/body bounds, stable error mapping, bounded retry classification/backoff.

**Integration/E2E tests:** Actual handler tests for two users + anonymous/expired/revoked/removed allowlist, SQL role constraints, balances, linked audit, forced rollback, key conflict and lost response.

**Security and concurrency regression tests:** Body/query/header identity spoofing, workspace/account scope mismatch, rejected draft references, CSRF/origin bypass, archive races, duplicate-key contention, deterministic real 40001/40P01 abort and successful full retry.

**Failure/edge cases:** SQL commit error after callback succeeds, response lost after commit, insufficient pool timeout, request hash protocol version, changed archive state, invalid FX or JS-number input, unexpected error redaction.

**Rollback/migration notes:** No destructive migration. Keep financial exposure disabled and published grants SELECT-only; retain the normal route’s null write capability on failure (there is no production enable flag). Preserve committed receipts/audits and retry with identical key, never re-post blindly.

**Definition of done:** Behavior demonstrated; strict validation and session-derived authorization; atomic ledger/receipt/audit rollback; additive/checksum-safe migrations with recovery; required formatting/lint/typecheck/unit/integration/build checks green; applicable browser/accessibility checks; accounting/security review at the final head; reviewed merge. Compilation, an agent review, or a tracking issue alone is not completion.
