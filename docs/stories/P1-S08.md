# P1-S08 — Income, expense and transfer commands

**ID:** P1-S08 (#38) | **Epic:** P1-E4 (#37) | **Priority:** P0 | **Dependencies:** S07 reviewed merge `1fd3b936a3ccdce2194bc5b6be2fa769acaa0318`; S05/S06 accounting engine retained.

**User story:** As an allowed owner, I can record activity through typed transaction entry and see persisted history, correct balances, net worth effects and consumption classification.

**Inputs:** Server-derived session, owned workspace/account, scoped idempotency key, positive exact INR decimal amount, effective date, income/expense category and optional description. Transfers require distinct eligible owned accounts; loan commands separate principal and interest. Caller-supplied ownership, raw posting legs and unsupported currencies reject.

**Outputs:** Typed financial services/handlers, responsive transaction entry/history, ledger-derived consumption queries, additive immutable capture context, tests and reproducible browser evidence.

## Acceptance criteria (Given / When / Then)

1. Given SBI Savings with ₹50,000 opening, when an ₹850 Groceries expense saves, then history shows one purchase and persisted balance is ₹49,150 after refresh.
2. Given an active owned bank/cash account, when income saves, then debit asset / credit income increases the normal asset balance and income total.
3. Given a card purchase, when saved, then debit expense / credit card increases liability and consumption; settlement later reduces liability and bank assets without another expense.
4. Given owned distinct eligible accounts, when transferring or funding an FD, then assets move without consumption or net-worth change; self-transfers reject.
5. Given a loan payment, when principal and interest post, then principal reduces debt and interest increases consumption, with exact cash and net-worth effects.
6. Given duplicate submissions/lost responses, when authorized same-key recovery runs, then exactly one journal/receipt/audit/capture exists and the original result replays after rename/archive; changed payload conflicts.
7. Given a wrong owner, expired/revoked session, archived account, invalid type/currency or forged raw fields, when saving, then no financial or classification side effect survives.
8. Given posted reversals, when consumption is calculated, then reversed expense/income nets out through ledger postings; history retains the original capture and reversal context.

**Unit tests:** Exact parsing/canonical hashing, bounded amounts/date/description and strict category/type contracts; subsequent slices add transfer/FD/loan template cases.

**Integration/E2E tests:** `transaction-capture.test.ts` runs real authenticated Request handlers on actual restricted local writer roles in public/private schemas. It covers exact maximum quantity, card signs, two-owner denial, canonical replay, concurrency, reversal summaries and staged atomic failure. `transactions.spec.ts` covers desktop/mobile real UI, refresh, persisted balances, accessibility and lost-acknowledgement recovery. Reuse existing S06/S07 concurrency, cancellation, session, migration and attestation regression suites.

**Failure/edge cases:** Amount overflow/precision, stale account selection, unsupported categories, same-key conflict, ambiguous COMMIT, cancellation, late errors, archived replay, future effective dates (history retained; current totals include effective postings through now). UI pending identity is retained for the current mounted page; a refresh during an uncertain result currently requires inspecting committed history rather than blindly resubmitting. Durable browser pending storage is not yet implemented.

**Rollback/migration notes:** Migration 010 is additive; migrations 001–009 remain unchanged. Capture rows are immutable scoped evidence, not balances. Take a verified backup before future approved upgrades. Recover a failed deployment by keeping writers disabled and rolling application code back; retain posted rows/receipts/audits and applied migration history. Never destructively remove committed accounting evidence. Fresh/private upgrade rehearsals and checksum/drift checks remain mandatory.

**Definition of done:** All A–D behavior demonstrated in real UI/services, exact balanced and authorized mutations, atomic audit/receipt/context, safe recovery, tests/build/accessibility/states, docs, owner independent review and approved merge. Local acceptance never enables hosted or production financial writes. Phase 1 additionally requires S09 and its gate.
