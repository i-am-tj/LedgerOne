# P1-S06A — Financial command controls, audit schema and invariant attestation

**ID:** P1-S06A | **Title:** Financial command controls, audit schema and invariant attestation | **Epic:** [P1-E3A](https://github.com/i-am-tj/LedgerOne/issues/3) | **Priority:** P0 | **Dependencies:** P1-S05 reviewed and merged; A05-01/A05-02 contract selection documented

**User story:** As an allowed owner, I want to have provable SQL protections and auditable command outcomes before implementing financial APIs.

**Inputs (data/API/preconditions):** Version-6 schema, approved INR-only policy, private atomic draft strategy, catalog/privilege baseline and finding A05-03.

**Outputs (UI/API/schema/docs):** Additive migration(s) for financial audit action/context and correction-target defense; invariant catalog comparator/mutation tests; command/audit contracts. No financial HTTP write route.

**Implementation tasks:**

- [ ] Specify private atomic command drafts; reject persisted draft IDs/revisions as unsupported input.
- [ ] Add scoped audit target/operation context and financial actions without weakening append-only history.
- [ ] Reject CORRECT reversal predecessors in the same operation; retain exact multiset and acyclic predecessor guards.
- [ ] Compare fresh-replay vs target CHECK definitions/validation, trigger enabled state/definitions, function body/security/search_path, ownership/grants and migration names/hashes.
- [ ] Add fail-closed pre-write attestation contract and protected runtime privilege expectations.
- [ ] Run fresh public/private-schema migrations, baseline tests and negative drift mutations.

**Acceptance criteria (Given/When/Then):**

1. Given disabled triggers, changed CHECK definitions or changed helper bodies, when attesting a database, then report FAIL before any write enablement even if Prisma diff is clean.
2. Given financial audit action and scoped operation/target, when valid, then insert append-only evidence; foreign operation/owner links and destructive edits fail.
3. Given CORRECT targets its own operation replacement, when committing, then reject with no surviving receipt/journal/audit.
4. Given migrations 001–006 were applied, when upgrading/rehearsing, then their bytes/checksums remain unchanged and no runtime financial DML grant is broadened.

**Unit tests:** Normalized catalog comparison, deterministic manifest serialization, missing/extra/changed object diagnostics, audit DTO validation.

**Integration/E2E tests:** Fresh and existing fixture DB migration, checksum verification, constrained role audit inserts, exact correction positives/negatives, repeated attestation.

**Security and concurrency regression tests:** Scratch-only disable each trigger, alter CHECK and function, change search_path/security attributes/grants; detect all. Migration owner remains trusted; runtime cannot disable protections.

**Failure/edge cases:** Catalog normalization across private/public schema, extra/missing/unfinished migrations, unknown manifest version, stale pool after migration, connection/attestation failure.

**Rollback/migration notes:** Additive forward migrations only; backup/forward repair for a deployed upgrade. Disable exposure on attestation failure; preserve old applied SQL and immutable audit/history.

**Definition of done:** Behavior demonstrated; strict validation and session-derived authorization; atomic ledger/receipt/audit rollback; additive/checksum-safe migrations with recovery; required formatting/lint/typecheck/unit/integration/build checks green; applicable browser/accessibility checks; accounting/security review at the final head; reviewed merge. Compilation, an agent review, or a tracking issue alone is not completion.
