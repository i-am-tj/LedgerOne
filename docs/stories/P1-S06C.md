# P1-S06C — Authorized exact REVERSE and CORRECT commands

**ID:** P1-S06C | **Title:** Authorized exact REVERSE and CORRECT commands | **Epic:** [P1-E3B](https://github.com/i-am-tj/LedgerOne/issues/4) | **Priority:** P0 | **Dependencies:** P1-S06B reviewed merge with POST/replay/audit/retry tests green

**User story:** As an allowed owner, I want to undo or replace the exact requested transaction safely while retaining its posted history.

**Inputs (data/API/preconditions):** Verified session, scoped idempotency key, explicit original journal ID, effective date/reason; CORRECT supplies only validated replacement data. No client-provided reversal legs or operation/owner IDs.

**Outputs (UI/API/schema/docs):** Actual REVERSE/CORRECT handlers and services reusing validated ownership/hash/retry/audit machinery; immutable linked history and exact outcomes.

**Implementation tasks:**

- [ ] Lock original journal and referenced/replacement accounts in documented deterministic order; authorize full scope inside transaction.
- [ ] Reject unposted, foreign, already fully reversed, own-replacement or unsupported archived-account targets.
- [ ] Generate exact opposite posting multiset server-side, preserving duplicate multiplicity and original units.
- [ ] Create CORRECT reversal of the explicit original plus exactly one GENERAL replacement in one operation; no replacement can be the original.
- [ ] Record financial operation/target/reason atomically and replay the original outcome/audit on retries.
- [ ] Support documented reversal-of-reversal chains without allowing circular links; keep original provenance/read status intact.
- [ ] Test repeated opening corrections by retaining the original marker and GENERAL replacement against equity; no account/opening UI exposure.

**Acceptance criteria (Given/When/Then):**

1. Given REVERSE of an owned posted original, when committed, then the exact multiset negates it, one full reversal exists and original rows remain unchanged.
2. Given CORRECT names original O, when committed, then its reversal references O and one replacement commits with its audit; same-operation replacement cannot be O.
3. Given concurrent reversal/correction attempts against one original, when executed, then at most one succeeds and losers leave no ledger/receipt/audit side effects.
4. Given foreign/unposted/archived/duplicate targets, malformed replacement or injected reversal legs, when called through real handlers, then reject atomically.
5. Given identical retry after success/lost response, when called again, then return the same linked outcome with no additional financial audit.

**Unit tests:** Exact reversal multiplicity, canonical hashes for target/kind/replacement, correction outcome mapping and strict errors.

**Integration/E2E tests:** Real handler two-user negative tests; exact balances/links/operation/audit; injected failures before/after each stage and deferred commit; opening provenance chains.

**Security and concurrency regression tests:** Own-replacement correction regression A05-02; stale original already reversed, cross-owner target/replacement, concurrent reverse-vs-correct, serialization/deadlock retry, archived target and graph cycle negatives.

**Failure/edge cases:** Reversing a reversal, replacement fails after reversal built, duplicate lines, correction root opening balance, lost response, uncertain commit, archived original accounts.

**Rollback/migration notes:** Exposure remains disabled until final gate. Roll back by disabling handlers; preserve original/reversal/replacement and audit history. Never delete or mutate a successful correction.

**Definition of done:** Behavior demonstrated; strict validation and session-derived authorization; atomic ledger/receipt/audit rollback; additive/checksum-safe migrations with recovery; required formatting/lint/typecheck/unit/integration/build checks green; applicable browser/accessibility checks; accounting/security review at the final head; reviewed merge. Compilation, an agent review, or a tracking issue alone is not completion.
