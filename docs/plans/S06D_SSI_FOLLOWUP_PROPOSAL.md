## What is established

Parameterized batching reduces measured 50/500-leg insertion costs and all single maximum-size cells now succeed. It does not remove four-way errors: actual PostgreSQL serialization aborts still exhaust three attempts for disjoint two-leg POST/REVERSE and other representative cells. The 48-case batch campaign has four failed required tests, 18 failed measured requests in the full mixed/challenge campaign. The fixed three-attempt policy, full authorization per attempt, 10s execution/2s SQL/1.5s lock bounds and accepted 500-leg/1,000-account maxima remain unchanged.

Actual runtime SIReadLock samples include shared index page/relation granularity even when logical account sets are disjoint. Standalone equivalent receipt/result/validation EXPLAINs use existing indexes; adding an index merely because errors exist would be unsupported. PostgreSQL's SSI may conservatively reject concurrent work based on read/write dependencies and coarsened predicate locks. [PostgreSQL 17 isolation reference](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-SERIALIZABLE). This is a plausible contributor, **not proof of a unique conflict graph**. The source retains repeated per-row journal revision and deferred validation work; insertion batching intentionally does not bypass it.

1. Keep the current runner/financial SQL/invariants fixed. Improve fixed-label phase attribution of real 40001 errors to receipt, account/provenance, result, journal seal, audit and deferred COMMIT. 2. On generated disposable loopback targets only, compare fresh versus preloaded synthetic history/cardinality and default versus explicitly refreshed statistics. 3. Use the existing disjoint POST2/c4 and failing REVERSE50/c4 cells, with the same commands, 3 attempts and deadlines. Observe actual predicate locks and conflict phases without holding extra financial locks. Keep diagnosis samples separate from timing qualification; diagnostic hooks change timing. Bound each experiment to 32 requests and 90s, total 10 minutes, reusing the existing local-only storage/fixture guard and graceful cleanup.

If evidence identifies an unnecessarily broad query or repeated validation bottleneck, publish a precise candidate change with a trigger/FK-aware lock matrix, security/correctness proof obligations, before/after plans and the exact migration/attestation implications **before implementing it**. Any schema/function change must be additive with 001–007 checksums intact and fresh/upgrade tests. No such change is bundled in batching PR30 without separately accepted scope.
5. If query-plan work cannot meet capacity, bring a separately reviewed admission/serialization or operational-envelope design to the owner. Do not implement workspace-wide serialization casually: acquisition before versus after a SERIALIZABLE snapshot, multi-process behavior, cancellation, bounded queueing, lock ownership/cleanup, replay and ambiguous COMMIT need explicit design. Do not increase retries or shrink concurrency/leg limits as an undocumented workaround.

## Acceptance and stop conditions

A diagnostic result must distinguish observation from causal inference and include negative/failed/unmeasured outcomes. No discovered resource is force-dropped/terminated; close only owned clients and refuse cleanup if an active connection remains. An experiment that changes correctness/privileges or exceeds the approved resource bound stops and records FAIL.

Any later correction must retain exact monetary quantities/multiplicity, server-derived ownership/original, all per-row/deferred protections, immutable audit/receipt binding, fresh authorization/snapshot recovery, INR-only and native null capability. Repeat the full pipeline plus identical matrix/critical/max stress; all required cells and qualified critical tails must pass before capacity is accepted. Statistical uncertainty and hosted-dependent evidence cannot be filled by local CI. New accounting/security review and owner decision remain mandatory; neither this proposal nor batching approval is final merge permission.
