## Current path from statement to settlement

The following inventory uses the installed **001–007** definitions. Trigger names identify catalog objects. PostgreSQL also creates internal referential-integrity triggers for FKs. Here those FKs are non-deferrable and RESTRICT changes of the referenced financial identity. PKs, unique indexes, NOT NULL, enum types and CHECKs apply independently of the user-defined deferred triggers. Workspace and auth identities come from 002–003. Migration 005 pins the ledger function lookup path to pg_catalog, the installation schema, then pg_temp. Migrations 006 and 007 replace specific function bodies in that path. A full version token for arbitrary public draft edits is absent. The service avoids that surface through private atomic drafts. The revision write is nevertheless necessary to invalidate stale snapshots across concurrent leg changes. ### What is redundant

For a new journal with L inserted legs, one draft INSERT + L parent revision UPDATEs + L posting INSERTs + one seal UPDATE = **2L + 2** journal assertions in the deferred event queue. At L=500, CORRECT has two children and queues **2 × 1,002 = 2,004** such events. There is separately one receipt and one audit event. This count excludes internal FK work and the immediate draft/identity guards. During ordinary deferred COMMIT, each group of 1,002 resolves the same immutable posted child and repeats its sum, archive checks, operation count and, for the reversal, multiset comparison. The RCA measured COMMIT and standalone assertion cost; the event count is derived from the trigger definitions, not a runtime profiler count.

That equivalence assumes one unchanged final state at the evaluation boundary. PostgreSQL can fire pending constraint triggers at SET CONSTRAINTS IMMEDIATE and can subsequently defer new events. At an earlier boundary a draft may legitimately remain incomplete. The receipt may not be incomplete when its own constraint is flushed. Definitions can be selected by name, not just ALL. Tests must cover both modes. Deferrable constraint triggers are AFTER ROW triggers. A WHEN predicate is evaluated when the row changes, before a qualifying event is queued. Ordinary statement triggers and transition tables observe statement boundaries. [PostgreSQL 17 CREATE TRIGGER](https://www.postgresql.org/docs/17/sql-createtrigger.html) · [SET CONSTRAINTS](https://www.postgresql.org/docs/17/sql-set-constraints.html)

## Alternatives

**A — Schedule one full assertion on the seal transition.** Keep the journal constraint trigger name and use an AFTER ROW UPDATE constraint trigger whose WHEN predicate selects OLD DRAFT and NEW POSTED. Its deferred callback re-reads the journal by immutable scope/ID and fails closed if the expected posted row is absent. Every new posted journal must cross this transition exactly once: INSERT POSTED is prohibited, POSTED cannot be changed/deleted, and legs and markers cannot move or be mutated after sealing. Savepoint rollback discards the transition and its deferred event along with the row changes. Multiple drafts, edits, receipts or journals in one transaction each follow this rule independently. No executor hook, new table, transaction identifier, GUC or client-owned queue participates.

Retire heavy child-event callbacks on posting/marker and draft-only callbacks only after proving coverage. Inventory named SET CONSTRAINTS callers first. Removing old names would break named statements and could change **which** validation runs early. If named child-trigger flushing is a supported contract, preserve its semantics (including detection of invalid posted rows at the requested boundary), or obtain explicit compatibility approval. A no-op trigger under an old name is insufficient. Until that decision, a named-flush counterexample blocks adoption. Retain the existing full assertion and its nested operation check at seal; retain the independent receipt event even when there are no children. A later seal attaching an extra child to an existing receipt therefore also rechecks operation shape. Estimated ordinary maximum is **two full journal assertions**, with two nested shape checks and one independent receipt check. All 1,000 revision writes and immediate row guards remain.

**B — Coalesce within each existing constraint family (recommended for a prototype).** Immediate AFTER row triggers register scoped parent IDs for journal, posting and marker mutations. Use a separate pending entry for each transaction, journal and original constraint family (journal, posting, opening). A journal revision and the corresponding posting must register in their respective families. Other sessions must never consume this transaction’s entry. Preserve one independently addressable constraint name per family in the installation schema. A real deferred constraint trigger on entry insertion validates current rows and consumes the entry. Any mutation after an early flush must enqueue again. Savepoint rollback must restore both queue and financial rows; handle draft delete/recreate, same ID across transactions, OLD/NEW parent identities and multiple receipts. Preserve the independent receipt/audit events and the same row guards. A statement-level trigger could collect affected IDs into this protected queue, but could not supply the deferred check itself. For the default maximum CORRECT, the journal and posting families each have one pending entry per child: four full assertions. OPENING can require three per sealed journal. Multiple explicit flush boundaries can require more. Registration adds unique probes and a few transactional writes. Immediate mode may flush at every statement. This adds catalog objects, cleanup, contention and roles: clients must be unable to insert/delete/suppress registrations. A narrow trigger-owned privilege design, pinned resolution, no PUBLIC execute/DML and separate tests of role inheritance would need review. Extra queue/index locks change the lock graph. Use separate transition registration and dequeue tests for each original constraint mode. Prove forced IMMEDIATE from the start, nested triggers in one statement, and named lookup after moving constraints to an internal table. Keep the original private helpers inaccessible to application roles. Reject the prototype if early statement ordering or a pending privileged callback lets a client suppress validation.

**C — Retain current triggers.** Lowest compatibility risk and no DDL. Inserts are already batched. Unchanged receipt/leg/audit protections continue to work, but maximum first-response reliability currently fails. Increasing the three-second driver wait would change acknowledgement and resource behavior and would leave the repeated database work in place.

### Why a single seal event is insufficient for full direct-SQL compatibility

Consider a transaction with valid receipt, postings, seal and audit, followed by a named flush of **only** journal_balanced_at_commit and then an archive of a participating account before COMMIT. In 007, a posting_balanced_at_commit event still checks the posted journal against the archived account and rejects. In A there is no remaining child event. The transaction can become durable. This counterexample follows from the definitions; it has not been executed as part of this design-only work. Repository search found no named SET CONSTRAINTS application caller, but direct SQL is explicitly in scope. **Do not implement A as a drop-in replacement.** B preserves an independently pending posting-family witness in this schedule. All-IMMEDIATE mode is a different baseline: once all existing events have run, a subsequent same-session archive has no pending check in 007 either. Preserve that distinction and test it.

For B, the unique registration key must have database-generated transaction identity, scope, journal ID and family. Store registrations in protected permanent tables on the same database/transaction as the mutation; specify transaction-ID lifetime/wrap behavior and ensure no committed queue debris. At evaluation, validate the current parent (return for draft/absent as today), then consume only that transaction’s exact entry. Re-register after early consumption. Releasing or rolling back a savepoint must release or restore registrations and validation effects together. Avoid advisory locks, caller-provided tokens or session/temp state surviving a pool checkout. At positive default COMMIT each nonempty family requires one assertion per distinct final parent. Receipt and audit stay independently queued on their own tables.

### Boundaries the prototype must prove

- **Archive ordering.** Preserve immediate account checks, sorted FOR SHARE inside full validation, and the handler's sorted FOR UPDATE union before original lock. Locks survive an early flush until transaction end and serialize an independent archiver; a session does not conflict with its own locks. Test seal→archive in the same transaction with default deferral (reject), archive committed in a later transaction (allow and retain replay), and archive/unarchive before evaluation (validate actual state). For a forced early flush followed by same-session archive, compare 007 and candidate with **each named constraint and ALL**. A remaining 007 event may still reject at COMMIT. A candidate that accepts a previously rejected schedule fails. Restricting runtime grants is insufficient to prove direct-SQL equivalence. If the strong rule must also forbid archive after flushing every event in the same transaction, design a separate database-side archival rule with S07; no assumption that a deferred trigger is unconditionally last.
- **Receipts and audits.** Proposed companion check on the independent **new receipt INSERT event**, in addition to the current shape check: every new POST, REVERSE or CORRECT must have exactly one correctly scoped financial event with the required actor/action/reason/target. Keep audit-side validation, uniqueness, actor and FK checks. It must reject omission even when direct SQL assembles a balanced journal. Evaluate existence/identity at the chosen constraint boundary; forced early receipt checks may reject until the audit exists. Under default deferral, any legal insertion order that meets immediate FKs can finish before validation. Never retrofit an invented actor or reason to historical receipts. The callback runs only for newly inserted receipts; later replay of historical evidence retains its existing policy. Legacy workspace audit and unexposed OPENING retain 007 semantics. S07 owns an OPENING audit contract before an exposed command. This is a **separate tightening** of 007 and requires express approval, fixture classification and compatibility review. Keep audit presence out of the reused journal assertion so checking a historical receipt does not introduce a retroactive requirement.
- **Trust.** Structural database constraints cover arbitrary DML under non-owner roles with relevant table privileges. They cannot verify an unstored authenticated request, detect fabricated but internally consistent data from a fully trusted writer, or protect against an administrator replacing constraints. Normal runtime retains SELECT-only financial privileges; only the synthetic restricted writer may rehearse commands. No public SQL function, raw posting API or new consumer privilege is needed.

## Migration, measurement and decision

If separately approved, create a **new** versioned migration in one DDL transaction. Verify 001–007 checksums first. Rehearse against a clean public fixture and generated private schema, then upgrade a populated 007 fixture with drafts, legacy unaudited receipts, opening markers, posted chains and financial audits. Perform the switch with no in-flight financial writers or pending deferred events, bounded DDL lock acquisition, and fail closed on incompatible state. Preserve posted data and historic outputs. Identify named triggers and direct SQL fixture dependencies before finalizing DDL. Check catalog event mask, timing, row level, enabled state, WHEN expression, deferrability, function definition/owner/search path, permissions, PK/FK/CHECK definitions and migration digest. Advance schema version and expected manifest atomically in the release process; incompatible application/schema versions refuse writes. Compare current and upgraded restricted-role grants. Rehearse failed migration rollback, restore from tested backup and, after a committed migration, a reviewed forward repair reinstating 007 validations. Never edit old migration files or acquire host privileges for measurement.

Measure on equivalent 007/candidate sources, seeded history, CPU quota, cache policy and restricted roles. Derive expected queued events from observed row changes; independently count assertion entries with disposable diagnostic instrumentation or isolated database-level function statistics (if separately authorized), subtract setup, and distinguish journal, operation and audit functions. For B expect four full posted assertions on maximum CORRECT and two on POST/REVERSE under default deferral, plus cheap callbacks that return for unsealed drafts. Measure registration overhead as well as queue drains. A would need only two and one respectively, but fails the selective-flush example. Default operation shape still runs once per posted child plus the receipt event. Report actual function total/self SQL time separately from server COMMIT activity, client COMMIT acknowledgement and HTTP response. Nested timings overlap. Sample DB process/container CPU deltas and lock waits/predicate granularity only on the owned fixture. Record sampling overhead, runs where attribution is unavailable, 40001/40P01 and retry exhaustion. Never grant monitoring powers to the command writer. Separate traced trials from uninstrumented capacity tests.

Four vs 2,004 full assertions would remove about 99.8% of these invocations in the maximum deferred case. It does not eliminate per-leg guards, row locks, revision writes, FK work, WAL, network/driver timing or SSI. Require equivalent before/after command and COMMIT distributions, complete failure denominators and positive first responses. Enforce the accepted c1/c2 representative p95s, 1,000 observations for POST2/c2 p99, and at least three initial 201s per mandatory uncontended maximum case plus exact-head CI. Record any 503 as a failure even when replay finds a durable operation. Run stress/overload recovery, full S05–S06C regressions and independent accounting/security review before any capacity decision.
