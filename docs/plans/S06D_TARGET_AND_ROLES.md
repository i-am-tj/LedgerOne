## Target identity and connection contract

Record project reference, database, private schema `ledgerone`, PostgreSQL version/extensions, region, runner region/network, direct/session/transaction mode, host/port allowlist, TLS verification/CA, role identities/membership and fingerprint of the approved schema/history/ACL manifest. These values are **TBD**, not inferred from `.env` during planning. No selected target or production domain is claimed configured or verified. Prefer a dedicated disposable project/database with no real financial records; a mere schema on a shared live database is not assumed adequate isolation.

Supabase distinguishes direct, session-pooler and transaction-pooler modes; transaction pooling changes session-state and prepared-statement behavior. Choose and test the exact mode instead of treating ports as interchangeable. Prefer direct connection for migrations and a reviewed direct/session mode for the initial persistent verification runner; if transaction pooling is intended later, require its own compatibility evidence. Do not buy an add-on or change plans implicitly. [Official connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

Current `src/lib/profile.ts` enforces private production schema, recognized migrator/app identities and TLS `verify-full`; migration connections exclude transaction-pooler port 6543. The existing disposable writer is loopback/test/public-schema only. Neither constitutes a configured hosted financial writer. D-T02 must design an offline verification-only composition with explicit target approval, safe schema qualification and the same verified command engine; keep existing production app profile, published grants and native null capability unchanged. No environment variable or general feature flag may turn native routes into raw writers.

## Rehearsal and attestation sequence

1. Validate approved manifest without connecting; reject wrong schema/host/role/mode, unsafe TLS, absent permission and missing budget. Separate secret transport from committed non-secret manifest.
2. In local disposable DBs, apply untouched 001–007 fresh and upgrade from the predecessor, then any separately reviewed additive successor. Compare repository bytes to protected baseline and applied checksums; reject missing/extra/unfinished/changed history.
3. Build schema-qualified reference catalog from the same approved migrations. Compare normalized semantic definitions, not volatile OIDs or cosmetically normalized text that hides relevant changes. Check constraint expressions/validation/deferability, trigger definitions/enabled state, function bodies/security/search paths/ownership, schema ACLs, effective role memberships and grants.
4. On the actual approved target, read its history/catalog with the actual verifier. A reference rehearsal alone never attests that target. Unknown version, unavailable verifier or mismatched privilege/profile fails before command or replay. Re-attest after provisioning/role changes and on the existing fresh-command/replay path; do not cache across unapproved DDL.
5. Use actual restricted roles and real authenticated HTTP handlers to prove positive POST/R/C and negative owner/session/scope/privilege behavior. Direct privileged SQL fixtures alone do not prove authorization. Repeat exact prepared statement/search_path/session/transaction behavior in the selected connection mode.
6. Mutate constraints/triggers/functions/roles/history only in explicitly disposable test fixtures to verify drift detection; never in a real financial schema. Hosted negative fixtures require O-HDDL/O-HWRITE as applicable. Preserve the normal runtime and INR restriction.

A privileged administrator changing data/catalog between attestation and use remains a trust boundary; this is not cryptographic proof against the database owner. Runtime roles must not have DDL, operational DDL must be exclusive/reviewed, and the report must state the residual race and incident behavior. Catalog detection does not reconstruct tampered historical rows; canonical semantic binding and immutability tests remain mandatory.

## Cleanup and failure behavior

Give each campaign an explicit owned-resource registry and unique database/role/application identity. Close request streams, sockets, clients and pools created by that campaign, including both ends of lost-ACK proxies. Cancel only its own query/client; do not call `pg_terminate_backend`, force-drop, kill a process or revoke privileges belonging to unrelated/active sessions. Administrative cleanup must verify target identity and ownership, close own pools and find zero remaining connections before a permitted normal drop. If any session remains or ownership is uncertain, stop, report retained resources and seek scoped owner action; never force cleanup.

Hosted teardown itself is an O-HDDL action and must be explicitly included. Financial history is not deleted from a shared target as fixture cleanup. Prefer disposal of the entire approved isolated target; preserve evidence before teardown. Failures retain normal-runtime denial, quarantine the verification composition and record unknown COMMIT outcomes for same-key recovery. No production cleanup is authorized.

**Required evidence:** fresh/upgrade L/P/H manifests and digests; actual-role success/denial matrix; pre-write and replay drift failures; hosted approval references; owned cleanup success plus unrelated-active-connection negative test. All remain NOT RUN for S06D.
